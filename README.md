# SecureBox — личный менеджер паролей

Статический веб-проект (HTML + CSS + JS) в стиле **«Стекло и глубина»**. Работает на GitHub Pages и смартфонах. Без JS-фреймворков, без внешних CDN и трекеров.

> **Осторожно:** это самостоятельно разработанный прототип и он **не проходил независимый аудит безопасности**. Для критичных паролей, банковских данных и основных аккаунтов разумнее пользоваться проверенным менеджером, например Bitwarden или KeePassXC. Перед использованием реальных паролей проверьте код и настройку RLS. Не храните единственную копию данных только в браузере.

## Что умеет

- Создавать, редактировать и удалять записи, искать по названию, логину, категории и сайту.
- Категории, избранное, просмотр, копирование, переход на сайт.
- Генератор случайных паролей с использованием `crypto.getRandomValues`.
- Шифровать хранилище **AES-256-GCM**; ключ от мастер-пароля получается через **PBKDF2-HMAC-SHA-256 (600 000 итераций по умолчанию)** и случайную соль.
- Автоматически блокироваться через 5 минут бездействия.
- Экспортировать/импортировать **зашифрованную** резервную копию JSON.
- Работать локально или синхронизировать зашифрованный сейф через **Supabase Auth + Postgres + RLS**.
- Отдельный пароль облачного аккаунта и отдельный **мастер-пароль шифрования**.

## Вариант A — запустить локально

1. Скачайте файлы; `index.html`, `app.js`, `styles.css`, `config.js` и `assets/` должны лежать вместе.
2. Запустите на `http://localhost` или откройте через GitHub Pages (HTTPS). **На обычном `http://` без localhost Web Crypto недоступен.**
3. Выберите **«На этом устройстве»**, придумайте длинный мастер-пароль (лучше минимум 4–5 случайных слов либо 16+ символов).
4. Создавайте записи. Только **зашифрованный** сейф хранится в `localStorage` браузера; он **не** синхронизируется между устройствами.
5. В «Настройках» регулярно экспортируйте зашифрованный JSON. Очистка браузера удаляет локальную копию.

## Вариант B — облачная синхронизация на разных устройствах

### 1. Создайте Supabase-проект

1. Зарегистрируйтесь на [supabase.com](https://supabase.com), создайте новый проект.
2. В **SQL Editor** вставьте и выполните файл [`supabase.sql`](./supabase.sql): создаст `public.securebox_vaults`, ограничит права и включит RLS.
3. В **Authentication → Providers → Email** оставьте Email Auth включённым. Рекомендуется включить подтверждение почты. Для тестирования учитывайте почтовые лимиты бесплатного проекта.
4. В настройках API найдите **Project URL** и **Publishable key** (`sb_publishable_...`, либо legacy `anon` key). **Никогда не используйте `service_role` или `secret` key!**

### 2. Заполните `config.js`

```js
window.SECUREBOX_CONFIG = {
  supabaseUrl: 'https://ВАШ_ID.supabase.co',
  publishableKey: 'sb_publishable_ВАШ_ПУБЛИЧНЫЙ_КЛЮЧ'
};
```

Публичный `publishable`/legacy `anon` key **не секрет**. Доступ к таблице защищается **Auth + RLS**, а сами данные дополнительным шифрованием. Конфигурация видна посетителям GitHub Pages — это нормально **только** при корректном RLS.

### 3. Опубликуйте на GitHub Pages

1. Создайте репозиторий на GitHub (например, `securebox`).
2. Загрузите содержимое этой папки в корень репозитория. **Не добавляйте пароли, резервные копии и приватные токены в репозиторий.**
3. Откройте **Settings → Pages → Build and deployment → Deploy from a branch**.
4. Выберите `main` и `/ (root)`, сохраните.
5. Перейдите по опубликованному адресу, обычно `https://ВАШ-ЛОГИН.github.io/securebox/`.
6. В приложении выберите **«Облако»**, создайте аккаунт (e-mail + пароль), подтвердите почту, войдите и **отдельно** создайте мастер-пароль сейфа.
7. На втором устройстве откройте тот же адрес, авторизуйтесь **под тем же облачным аккаунтом** и введите **тот же мастер-пароль**. Все изменения должны появиться после обновления/повторного открытия; также есть кнопка синхронизации.

**Настройки URL в Supabase Auth:** для обычного подтверждения e-mail достаточно стандартного Site URL проекта; после подтверждения вручную вернитесь в приложение и войдите. При желании задайте Site URL вашего GitHub Pages в **Authentication → URL Configuration**. Приложение не обрабатывает OAuth callback и не предлагает восстановление мастер-пароля.

## Важные ограничения безопасности

1. **GitHub Pages — только сайт**, не база данных. Облачный режим работает исключительно после создания вашего проекта Supabase.
2. Сервер видит аккаунт, время запросов, размер и версии зашифрованного сейфа. Он **не должен** получать мастер-пароль и содержимое записей.
3. Мастер-пароль не сохраняется, не восстанавливается, не отправляется в Supabase. Если забыть его — старые данные не восстановить. Восстановление пароля *облачного аккаунта* не поможет расшифровать сейф.
4. В приложении есть защита от одновременной перезаписи: при конфликте версий сохранение отменяется. Обновите сейф и повторите изменение. Не редактируйте один и тот же сейф сразу на двух устройствах в офлайне. В облачном режиме офлайн-редактирование не поддерживается.
5. Копирование пароля в буфер обмена может раскрыть его другому ПО. Приложение пытается очистить буфер через 20 секунд только при наличии разрешения и только если в буфере всё ещё находится тот же текст.
6. JS в браузере имеет доступ к расшифрованным данным во время работы. Вредоносное расширение, заражённое устройство, XSS, взломанная учётная запись GitHub с изменением опубликованного кода — риски, от которых эта архитектура полностью не защищает. Не добавляйте сторонние скрипты и аналитику на страницу.
7. `sessionStorage` временно сохраняет **облачную Auth-сессию** в текущей вкладке. **Мастер-ключ** и открытые пароли сохраняются только в оперативной памяти JS до блокировки/закрытия страницы; скрипты и расширения браузера, имеющие доступ к этой странице, всё равно могут их увидеть.
8. Резервная копия зашифрована, но доступна для офлайн-перебора мастер-пароля. Нужен длинный и уникальный пароль. Импорт заменит сейф полностью и потребует пароль от импортированного сейфа.
9. Не делитесь резервной копией, не публикуйте её и не вставляйте в GitHub, даже зашифрованную.
10. Для длительного использования необходимы независимый аудит, тестирование политики доступа, проверки обновлений и продуманная процедура восстановления/резервирования.

## Несколько технических решений

- Внешние шрифты/скрипты/картинки не загружаются, Content Security Policy запрещает загрузку сторонних скриптов.
- Каждое шифрование использует новый 96-битный случайный IV, а пароль — отдельную соль для KDF.
- Cloud API использует `Authorization: Bearer <user_access_token>`, а RLS ограничивает все операции владельцем записи.
- В облако отправляется **один** JSON-объект с зашифрованным содержимым. Поиск происходит локально после открытия сейфа.
- Конфликтная запись определяется сравнением `version` при `PATCH`.

## Проверка настроек Supabase

Попробуйте войти пользователем A и пользователем B и убедитесь, что каждый видит только собственный сейф. Не отключайте RLS. Не используйте ключ с привилегиями администратора в `config.js`.
